# v2 agent循环超时对比（2026-10-13）

**结论：未找到稳定15秒内且满足上线质量的方案；不接API、不跑接线后的全量真实回归。**

先后插入的线上修复独立提交：f6940de（能源路由）；87dfe94/0d674fa（20秒分类和fallback mode）；72f8c2b（天气、公共工具分类先行、总负荷、一位小数、通用step移除）。它们没有启用原生agent循环。

## 试验设计与数据边界

- 固定相同10题：当前时间、本楼天气、当前能源、SOC、未来24小时峰值、24 °C费用比较、能源+SOC、天气+时间、两句复利知识、闲聊。输入见latency_cases.json。
- 全部目录20工具；常用目录6工具：get_time/get_weather/current_energy/current_state/forecast_peak/hvac_compare。样本能用这6工具回答，**不能据此声称覆盖91题**（告警、电梯、累计能耗、联网等都不在这6工具内）。
- 描述原样/压短仅更改description，不变name或JSON schema。全目录原样8,426 bytes，压短7,435 bytes；常用目录原样1,865 bytes，压短1,637 bytes；实际精确字节见逐组合JSON的tool_json_bytes。
- “轻量回复”定义为要求模型在同一次首步请求中，先给不含数据的一句话再调用工具；不是服务端立即播一句固定文案、不是额外无tools请求。模型并非总遵守：最佳组初轮仅6/10有实质过渡回复。不是靠过渡回复冒充完整回答成功。
- 2×2×2=8组合，每种都完成同样10题。额外旧8秒整请求限制诊断基线10题，初筛最佳组合另复测2轮，共110题、210次串行上游请求。没有并行多个Python进程或起实验后端；每个请求同步结束/本地client关闭后再开始下一请求，timeout timer取消并join。
- 使用草稿的SYSTEM、tool catalogue/adapters、数字校验、最多8步/最多一次重写/一次失败重试；独立同步计时runner替代旧线程wait_operation以免旧8秒截断遮蔽慢点。正式API和草稿agent_runner未接线或修改。
- 诊断组合每轮总30秒，不套旧首token8秒取消：才能测到22.9秒首响应和后续流式停顿。旧上限基线的失败响应不能解释为首token实际耗时=8秒。没有把预算延长叫做延迟优化。
- “首响应”指上游第一条实质content/tool-call delta。另存headers、first_sse、单请求完整耗时、工具耗时、每步序号、request bytes/hash、错误类别、答案及校验结果。first_sse可能只是role空delta，不能当首token。
- 成功初筛：完整非空回答+预期工具/参数+必须内容+没有校验后删句。保存的automatic_success只是筛查，不是上线语义质量批准。完整15秒成功另记，空回复、仅过渡语、超时不算。
- 每5题一批、逐题落盘、禁止重复覆盖已完成题。结果latency_results/；汇总latency_summary.json；命令和统计脚本latency_probe.py、latency_summary.py。

旧8秒整请求基线：成功8/10、15秒内成功7/10，整轮中位9.2秒/最大18.3秒；24次请求中4次（16.7%）到8秒未观察到token，不能把它们写成“0%首token超时”。

最佳初筛组合复测：
- 第一复测：自动成功8/10、15秒成功8/10，最大10.7秒；18次请求1次首token>8秒、另1次3.8秒空完成。
- 第二复测：自动成功9/10、15秒成功7/10，最大20.5秒；18次请求1次首token>8秒。
- 三轮合并30题：自动成功27/30（90.0%），15秒内成功25/30（83.3%）；56次请求2次首token>8秒（3.6%）。因此不能称稳定15秒内。
- 两条复利回答初筛仅因“利息”未逐字出现失败，人工语义复核属于误杀，可增记为29/30、27/30；原始结果不改。其他语义问题还会减分，详见质量检查。


## 超时卡在哪里

1. **第一次带tools就可能长时间无实质delta。** 20工具原描述/无轻量的天气题：首步22.9秒首响应/22.9秒完成，第二步3.1秒，整轮26.0秒；20工具原描述/有轻量的HVAC题首步30.2秒仍无token。此时多步尚未开始。
2. **工具完成后的第二步也可能长时间无token。** 20工具压短/无轻量的天气题首步6.8秒出token/7.0秒完成；第二步18.8秒才出token/19.1秒完成，整轮26.1秒。6工具原描述/无轻量的SOC题首步1.3秒，第二步16.7秒首token/17.0秒完成，整轮18.4秒。
3. **首token早不代表完整流早。** 最佳组合第二复测的复利题首token1.5秒，完整请求20.5秒，只有一轮且没有本楼工具。该观测能确定“token之后流式完成慢”，不能从客户端数据推断上游排队/计算/网络的具体内部成因。
4. **多步累加/校验重写会消耗预算。** 最佳初轮HVAC用了4个模型请求，累计11.9秒；能源+SOC第二步首token0.9秒但完整响应10.9秒，整轮13.5秒。旧基线能源第一请求8.2秒未出token、重试并查多工具，4请求累计15.1秒。
5. **本地工具不是本组主要耗时。** 各组工具单次最高32–63毫秒（本10题没有公网数据工具）。不据此推断web_search/city_weather的耗时。
6. 草稿agent_runner把`agent_stream(..., min(8., remaining))`当作请求期限，agent_provider用该期限覆盖整段流。wait_operation另有首token8秒门槛，且失败后可重试。上述11.8秒HVAC第二请求首token8.3秒、完整10.5秒，以及1.5秒首token/20.5秒完整知识题，均证明应该分别处理首token期限和剩余整轮期限；简单“首步先说一句”或延长计时不保证整轮15秒。

减少目录比仅压短描述节省更多请求字节，也消除了current_state/storage_history歧义；但8组合按时间顺序串行，样本小且上游波动明显，不是随机交叉的大样本因果试验。不能声称某一提示因素必然提升延迟。


## 质量检查及不接线的理由

自动初筛只验证工具集合/单位关键词/数字集合。人工读答案发现这些尚未解决的问题（不是本轮线上代码问题）：
- current weather有时选scope=today_remaining，工具适配器给了未来3小时，回答未来天气而非当前；初筛有°C和%仍会过。最佳复测weather/weather_time也出现此问题。
- 全目录组可能把SOC选到storage_history，输出0.4或累计电量而不回答当前SOC；缩小目录降低歧义，但不能用永久6工具代替全功能。
- HVAC有计入/排除时段遗漏或错误解释：最佳第一复测仅说今天4个排除时段，漏次日2个；6工具原描述/无轻量出现“24度时段多6小时”等错误。最佳第二复测还无证据推断供暖机理。数字集合通过不代表主体/字段/范围/原因正确。
- 初筛两条复利“收益滚入本金”解释确实有效但因为没逐字用“利息”而误杀，记录旁注，不篡改保存结果。
- 少数无tool时间直接用系统时钟回答，被初筛拒绝（用户需要工具来源）；另有一次空完成，与上游失败不同。
- 没有重测history/context、多轮跨问题证据、公共工具前守卫、新事件与v1前端兼容；不能靠本10题证明上线可用。
- 实验发生于多次线上小修之间，逐组合文件记录了固定输入和建模工具来源hash；没有使用API，因此线上等待预算和事件变动不进入此延迟数据。草稿SYSTEM仍旧“最多一位小数”时期，实验答案也未全面满足最新一位小数/公共工具先分类口径。

本轮已完成全部8组合、旧上限诊断基线、最佳2次重复。没有合格稳定方案，**本轮停止，不接API、不执行条件尚未满足的完整真实回归**。后续可选方向：把首token/完整轮分离；保留只读全目录通过按需分层暴露避免6工具功能缩水；修工具scope与字段/单位/时刻/范围语义校验；单独探索响应长度/连接复用/上游模型或队列性能。这些未实施也未声称有效，需下一步授权。
